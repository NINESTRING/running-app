# 자동 바퀴 수 감지(랩 카운트) 설계

날짜: 2026-08-24

## 문제

트랙이나 공원에서 같은 코스를 반복해서 도는 러닝(뺑뺑이)에서 몇 바퀴를
돌았는지 앱이 세어주지 않는다. 러너가 머릿속으로 세거나 km 스플릿으로
역산해야 하는데, 400m 트랙 인터벌이나 공원 루프 훈련에서는 바퀴 단위
기록(바퀴 수·바퀴별 랩타임)이 km 스플릿보다 훨씬 유용하다.

## 요구사항 (사용자 확정)

- **자동 감지** — 러너가 버튼을 누르거나 모드를 켜지 않는다. 수동 랩 버튼 없음.
- **항상 동작** — 모든 러닝에서 백그라운드로 감지한다. 루프가 감지되기 전에는
  UI에 아무것도 나타나지 않으므로 일반 로드 러닝에는 영향이 없다.
- **표시 범위** — 러닝 중 라이브 바퀴 수, 바퀴별 랩타임/페이스, 종료 후 요약
  표시, 바퀴 완주 시 음성 안내 전부 포함.

## 접근 방식: 루프 클로저 감지

경로가 이전에 지나간 지점으로 **같은 진행 방향으로** 돌아오는 순간을 감지해
그 지점을 게이트로 확정하고, 이후 게이트 통과마다 바퀴 수를 +1 한다.

검토했으나 채택하지 않은 대안:

- **시작점 반경 방식** — 러닝 시작 지점을 게이트로 고정. 구현이 가장 단순하지만
  집에서 트랙까지 워밍업으로 이동한 뒤 도는 흔한 시나리오에서 감지가 안 된다.
- **OS 지오펜싱(`Location.startGeofencingAsync`)** — 반경이 통상 100m 이상,
  이벤트 지연이 분 단위라 400m 트랙에 쓸 수 없다.
- **수동 랩 버튼** — 러너 부담. 자동 감지가 사용자 선택.

오감지의 주적은 **왕복(out-and-back) 코스**다. 같은 지점을 반대 방향으로
다시 지나는 것을 진행 방위각 비교(±90° 허용)로 걸러낸다. 8자 코스의
교차점도 방향이 다르면 같은 원리로 무시된다.

## 설계 1 — 감지 모듈 `src/lib/laps.ts`

순수 함수로 만든 증분(incremental) 상태 머신. GPS 포인트를 하나씩 먹이면
내부 상태를 갱신하고, 같은 코드를 저장된 `routePoints`에 순서대로 먹이면
배치 재계산이 된다(라이브와 저장 후 결과 동일 보장). 1초 tick마다 전체
경로를 재계산하지 않는다 — 스플릿 메모이제이션(commit `f3025fa`)과 같은 이유.

### 상태 머신

**1단계 — 루프 발견 (게이트 미확정):**

- 지나온 경로를 약 15m 간격으로 다운샘플한 후보점 목록을 유지한다.
  각 후보점은 위치, 경로 누적거리, 통과 시각, 통과 방위각을 가진다.
- 새 포인트가 다음 세 조건을 모두 만족하는 과거 후보점을 찾으면 루프
  클로저로 판정한다:
  1. 경로 누적거리 차이 ≥ 최소 랩 거리(150m)
  2. 직선 거리 ≤ 게이트 반경(25m)
  3. 방위각 차이 ≤ 90°
- 그 후보점이 **게이트**로 확정되고, 이 순간이 1바퀴 완료다. 랩 1의 시작
  시각은 게이트 지점을 처음 지난 시각(후보점의 통과 시각).
- 후보점 탐색은 선형 스캔으로 충분하다: 20km 러닝도 후보점 약 1,000개,
  포인트 유입은 3초에 1개.

**2단계 — 바퀴 카운트 (게이트 확정 후):**

- 게이트 반경 25m를 **나갔다가 다시 들어오는**(exit → re-entry) 순간 +1.
- 마지막 카운트 이후 누적 이동 거리 ≥ 150m를 추가로 요구한다
  (GPS 튐에 대한 이중 방어).
- 통과 시각은 기존 `computeSplits`와 같은 방식의 선형 보간으로 정밀화한다
  — 랩타임 정확도의 핵심.
- 랩타임은 스플릿과 동일한 규칙으로 일시정지 시간을 제외한다:
  `partitionPoints`처럼 일시정지 경계를 넘는 포인트 쌍의 시간 델타를
  0으로 처리한다(재개 직후 첫 델타 무시). 일시정지 중 포인트 자체는
  `runStore.addPoint`가 이미 버리므로(`status === 'running'` 가드)
  감지기에 들어오지 않는다. 배치 재계산 시에는 저장된 segments 정보로
  동일한 경계를 복원한다.

### 튜닝 상수

| 상수 | 값 | 근거 |
| --- | --- | --- |
| `GATE_RADIUS_M` | 25 | GPS 수평 오차 ~10m + 트랙 8레인 폭 ~10m 커버 |
| `MIN_LAP_M` | 150 | 200m 실내 트랙~작은 공원 루프 지원, GPS 지터 루프 배제 |
| `HEADING_TOLERANCE_DEG` | 90 | 왕복 재통과(방위각 차 ~180°)를 확실히 배제 |
| `CANDIDATE_SPACING_M` | 15 | 게이트 반경 25m 대비 충분히 촘촘, 메모리 절약 |

### 허용하는 한계 (의도된 동작)

- 코스를 이탈해 다른 곳에 다녀오면 카운트가 늘지 않을 뿐이고, 돌아와서
  게이트를 지나면 다시 +1 된다. 엄격한 경로 일치 검사는 하지 않는다.
- 러닝 도중 도는 방향을 반대로 바꾸면 게이트 방위각과 어긋나 카운트가
  멈춘다. 새 방향으로 게이트를 다시 발견하지는 않는다.
- 일시정지 후 게이트 반경 바깥에서 재개하면 다음 진입이 카운트될 수 있다.
- 게이트 통과 재진입은 `prevLast→p` 세그먼트가 게이트 반경에 닿는지로
  판정한다(점 p만 보지 않음). 단, 신호가 완전히 끊긴 구간이 그 세그먼트조차
  게이트 반경 25m에 전혀 닿지 않을 만큼 길면(직선거리 기준으로도 25m를
  벗어나는 GPS 끊김) 그 통과 자체를 놓친다 — 놓친 바퀴의 거리·시간은 다음
  바퀴 기록에 합산되어(두 바퀴 분량이 하나로 병합) 나타난다.
- 급격한 헤어핀 코스(대향 구간 간격이 게이트 반경 ~25m 미만이거나 회전
  폭이 전진 판정 창 ~30m 미만)에서는 전진 판정(`isMovingForward`)이
  유보되어 그 구간에서 루프 발견·재진입 판정이 되지 않을 수 있다.
- 랩 1은 게이트 반경 진입 시점을 기준으로 측정되어 이후 바퀴보다 게이트
  반경(~25m)만큼 짧게 측정된다(첫 통과 시점의 후보점이 이미 트랙 시작
  지점 근처이기 때문).

## 설계 2 — 러닝 중 통합 (store · UI · 지도)

- **구동 위치**: `runStore.addPoint`에서 감지기에 포인트를 먹인다.
  화면 tick이 아니라 store에서 돌므로 백그라운드에서도 동작한다.
  감지기 상태(바퀴 수, 게이트 좌표, 완료된 랩 목록)는 store에 둔다.
  `reset` 시 감지기도 초기화한다.
- **라이브 UI**: 게이트 확정 전에는 아무것도 표시하지 않는다. 확정 후
  러닝 화면의 구간 라인(`구간 N · pace`) 옆/아래에 `랩 N · M'SS"` 형태의
  랩 라인을 추가한다. 지표 그리드는 이미 2×2로 가득이므로 셀을 늘리지
  않는다.
- **지도 마커**: 게이트 확정 시 `RouteMap`에 게이트 위치 마커를 표시한다.
  코드베이스 최초의 `Marker` 도입이며, `RouteMap.web.tsx` 스텁도 함께
  미러링한다.

## 설계 3 — 음성 안내

- `VoiceCue` 유니언에 `'lap'`을 추가하고 `VoiceCueState`에 `lapCount`
  필드를 더한다. `nextVoiceCue`의 기존 불변식(같은 tick에 여러 마일스톤이
  겹치면 하나만 말하고 상태는 모두 전진)을 유지하되, 우선순위는
  **랩 > 거리 > 시간**으로 한다 — 트랙 러닝에서는 랩이 주 관심사다.
- 멘트: "3바퀴, 랩타임 2분 5초" 형식. 기존 `speakDuration` 재사용.
- 설정: `VoiceGuideSection`에 바퀴 안내 온/오프 토글 추가, 기본 켬.
  `settingsStore`에 키 추가 — persist는 shallow merge라 버전 범프 불필요.
- 종료 후 음성 요약(`voiceSummaryText`)에 바퀴 수가 있으면 한 문장 추가.

## 설계 4 — 저장·요약 표시

- **스키마 변경 없음.** 상세 화면(`app/run/[id].tsx`)이 스플릿을 저장된
  `routePoints`에서 재계산하는 것과 동일하게, 바퀴도 같은 감지 코드로
  배치 재계산한다. 라이브와 동일한 코드 경로이므로 결과가 일치한다.
- 상세 화면 헤더 지표 라인에 총 바퀴 수(예: `12바퀴`)를 추가하고,
  `SplitsList` 스타일의 바퀴별 랩타임 리스트(상대 페이스 바 포함)를
  스플릿 리스트 아래에 표시한다. 루프가 감지되지 않은 기록에서는 둘 다
  표시하지 않는다.
- 기존 기록에도 소급 적용된다(재계산 방식의 부수 효과).

## 테스트 전략

감지기가 순수 함수이므로 합성 GPS 경로 픽스처로 유닛 테스트한다:

- 400m 트랙 시뮬레이션(원형 좌표 생성) N바퀴 → 바퀴 수 N, 랩타임 오차 검증
- 워밍업 직선 이동 후 트랙 진입 → 게이트가 트랙 위에 잡히는지
- 왕복 코스 → 바퀴 수 0 (방위각 필터 검증)
- GPS 노이즈 주입(±10m 지터) → 오카운트 없음
- 일시정지 경계를 낀 랩 → 랩타임에서 정지 시간 제외 확인
- 라이브(증분)와 배치 재계산 결과 일치성

## 범위 밖

- 수동 랩 버튼, 랩 수동 수정/삭제
- 게이트 위치를 서버에 저장(재계산으로 충분)
- 코스 형상 일치 검사(트랙 이탈 감지)
- Supabase 스키마 변경
